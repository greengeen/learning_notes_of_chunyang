### 2. 对于git的理解

1、git 是分布式版本控制系统，可以在本地文件夹里保存每次代码的改动记录
2、版本控制记录每次改动的内容、作者和时间，方便回溯和合并；多人同时改同一处时仍然会出现冲突，它的作用是让冲突可见、能定位和解决
3、直接复制文件备份看不出两份文件具体差在哪几行，也无法自动合并，更没有作者和提交时间记录
4、git 是作用在本地的工具，而 github 和 gitee 是用来远程存放仓库、同步协作改动的网站
5、repository：仓库，一个项目的目录，包含它的版本历史
   commit：把当前文件状态提交成一个记录
   branch：从主线分出一条独立的流程，其上的改动不会影响 main
   merge：把改动的分支合并进 main，可能出现合并冲突



### 3. 关于git的命令行

```bash
git status                  # 看改动、暂存，每次提交前先跑
git add <文件>              # 把文件放进暂存区
git commit -m "说明"        # 附带提交记录
git push origin feature-UI  # 把本地提交推到远端对应分支
git fetch origin            # 拉远端最新状态，但不合并
git log --oneline -5        # 看最近五条提交
git branch -vv              # 看本地分支和远端的对应关系、领先/落后几个提交
```

分支、合并、仓库这些概念对应到项目里：仓库是团队共用的 GitHub 项目；我在 `feature-UI` 上干活；组长在 `main` 上；别人的 `feature/core` 各自隔离；最后通过合并把分支并进 `main`。

团队同步流程：克隆仓库到本地 → 从 main 建功能分支 → 小步提交 → push 到远端对应分支 → 开 PR 请求合并 → 组长审核后合进 main。

### 4. 关于使用习惯

- 每次提交前先 `git status`，不用 IDE 一键收全部
- 提交信息带前缀，说清改的是哪一类
- 合并前先 fetch，看清 main 改了什么
- 不 `push -f`，不改写已经推送的历史
- 不自己合并自己的 PR，等组长审核


## 二、AI Agent 基础认知与实践

### 1. LLM 和 Agent 的区别
- AI agent以大模型为核心，可自主拆解目标、调用工具等，可反复执行任务，能返回文字以外形式的结果
### 2. 除了 LLM，agent 还包含的内容有：
- LLM 底座，作为理解问题、生成文字的基础
- 工具调用：读写文件、执行命令、搜索、调用接口等，模型通过工具和外部环境交互
- 上下文管理（context）：决定哪些历史记录、哪些文件能被模型看到，以及阅读范围
- 任务规划：把大目标拆成可执行的小步骤，按步骤推进
- 记忆：保存任务过程中的信息和约定
- 执行边界与权限：限定模型能访问、能修改的范围，关键操作需要询问权限

### 3. 关于harness
- harness为更外层的运行框架，可决定（也可用户自行选择）该项目下模型使用哪个档位、调用哪些skill,访问和写入哪些file,以及用什么形式返回给用户
- 组织流程为：接收任务 → 模型思考 → 按规则调用工具 → 读取执行结果 → 继续下一步或交付；同时管理执行模式（标准/计划）、权限和工作区边界

### 4. 关于如何精准描述问题、规范上下文使 AI 高效工作
- 明确AI的角色定位及目标概要（一个主要目标）
- 明确项目背景（已有代码、接口名和字段名）
- 量化效果：进制范围、位数、色值、字号，而非给出“好看，美观”这一模糊概念
- 明确禁止项
- 可先进入计划模式，也可让它复述约束、目标内容，总之要确认 AI 的理解偏差在允许范围内
- 列举可检验的验收标准：输出结果，界面尺寸
- 长任务分布进行（可设置总goal+检查点）


### 5. 总结
AI Agent是当今学习必不可少的工具，但使用需明确作用边界，最重要的判断仍需人为操作


## 三、开发环境与工具资源


### 1. Learn Git Branching

链接：https://learngitbranching.js.org/?locale=zh_CN

把分支、合并、HEAD 移动这些概念变成可视化小关卡，每敲一条命令就能看到提交树怎么变。原来一直看不懂 `git branch -vv` 那串输出，玩两关就理解分支指向了某个提交。以后做 rebase 之前先在它上面练一遍，不拿团队仓库当试验场。

### 2. Git 交互式练习

链接：https://woyeyao.github.io/Git-Interactive-Tutorial/

中文的 Git 命令闯关，要求每条命令敲对才能过关。看视频容易产生"我会了"的错觉，实际操作时连 `git add` 后面跟什么都会卡住；这个练习强迫手不能停。以后忘了命令顺序，就回去过对应关卡。

### 3. VS Code Git Graph 扩展

在 VS Code 扩展市场搜 `Git Graph`，官方介绍：https://code.visualstudio.com/docs/sourcecontrol/overview

把提交历史画成图形，能看出哪个提交从哪个分支分出来、合并是怎么发生的。合并 `origin/main` 那次，我用图形一眼确认了自己分支和 main 的关系。以后做冲突演练和 PR review 时，用它确认分支从哪儿分出去、和对方重叠在哪。

### 4. AI Agent 工作台（deepseek harness/codex/opencode）

工作区绑定到项目仓库，能直接读写文件、跑命令。纯对话框里写代码要反复复制粘贴、自己解释文件结构；绑定工作区后它能自己读约定文件、自己跑 `py_compile`，闭环了。以后继续让它做生成和自查，提交和推送我自己来。

### 5. Python 官方文档（tkinter / ttk）

链接：https://docs.python.org/zh-cn/3/library/tkinter.ttk.html ，https://docs.python.org/zh-cn/3/library/tkinter.html

用来查控件的真实参数。AI 编造 `Frame.minsize` 那次，就是靠官方文档确认 `minsize` 属于窗口对象、不属于 Frame。被幻觉坑过一次之后，意识到官方文档是最便宜的权威来源。以后凡是涉及 API 是否存在、参数叫什么，先查文档再动手。

### 6. Pylance（VS Code 静态类型检查）

VS Code 扩展市场搜 `Pylance`，在运行之前就把方法不存在、类型不匹配这类错误标红。`frame.minsize` 那次运行直接崩溃，但 Pylance 在保存文件时其实已经报红了。以后固定成三段式：AI 改完代码 → 先看红线 → 再 `py_compile` → 最后运行。

### 7. GitHub 官方 Python .gitignore 模板

链接：https://github.com/github/gitignore/blob/main/Python.gitignore

一次性把 `__pycache__/`、`*.pyc`、虚拟环境目录这些不该进仓库的东西排掉。一开始不知道 `__pycache__` 会被 Git 看到，用 `git check-ignore -v` 验证命中之后才放心。以后每个新 Python 仓库第一件事就是放这份模板，再抽查两条规则是否生效。

取舍标准：上面只留了七个，判断依据是三条——我真的用它解决过一个具体问题；它替代了一个原本会浪费更多时间的动作；我知道下次什么时候会再打开它。各种 Git 命令速记图、AI 工具测评视频这类只收藏没打开过的，都没有列入。

## 四、学习总结

### 1. 最有价值的三点收获

1. 版本控制给我的不是安全感，是可追溯的能力。以前改代码怕改坏，就复制一份 `ui_备份.py`。备份只能回到上一个手动存的版本，Git 能回到任意一次提交，还知道那次为什么改。我实测过用 `git show` 把三天前的界面代码完整取出来，这个能力直接改变了我敢不敢做重构。感觉有时候用命令行更省事。

2. AI 提升的不是写代码的速度，是验证的成本结构。一开始我以为 AI 的收益是省打字。实际算下来，生成 465 行代码确实省了几小时，但它编造不存在的方法、声称加了其实没加、修症状留病根，这三次都让我明白：AI 把成本从"写"移到了"验"。真正的效率提升不来自让它多写，而来自我有多快的验证手段。定下"行数、关键字符串、像素宽度"三条客观指标之后，验一遍只要几十秒；没有指标，只能靠看起来还行，那等于没验（其实验收的方法也是AI告诉的）。

3. 约束不做什么，比说清要做什么更重要。第一版项目约定我只写了全项目说明，结果 AI 把别人负责的核心算法、事件调度、测试、README 全替我写了。加了一段明确的范围声明之后，它才老实只动界面层。要做什么是同向的愿望，不要什么才是边界。这个道理放到团队协作里同样成立。

### 2. 遇到的困难和解决过程

困难 1：不懂 Git 时，看不出自己在做危险操作。最开始我差点用 IDE 的提交按钮一次性收下所有改动，那会把 `test.cpp` 的删除混进"实现四区界面"这次提交，两件无关的事永久绑死。解决办法不是记住别用按钮，而是养成固定习惯：每次提交前 `git status`，看清楚暂存区里到底有什么。这个习惯后来救了我两次，一次是长中文文件名打错，一次是确认临时脚本没被加进去。

困难 2：AI 说已经改好了，但实际没有。第一次遇到我以为是偶发，第二次才发现这是模式。落下来的办法是：所有"AI 说改了"的结论，都用一条能命中具体字符串的命令验一遍。要求加 `minsize`，就搜行号；要求 450 行，就数行数。从验证它的总结，改成验证文件里的字节（或者最后输出结果的尺寸）。

困难 3：不敢做合并。看到"落后 main 1 个提交"的提示，第一反应是怕把别人的代码搞坏。实际做法分三步：fetch 只拉不合；`git log` 和 `git show` 看清对方改了哪些文件；判断和我改的是不是同一片区域；确认不会冲突才 merge。那次查明是新文件 `main.py`，零风险。理解冲突的真实规则之后，不敢合变成了知道该在哪儿小心。

### 3. 对 AI 使用的态度变化

之前我把它当成更快的搜索引擎和更快的打字员。现在我的定位是：执行力极强但没有责任心的合作者。它会把活干得漂亮，但它不会替我验收、不会替我判断需求该不该做、出错时也不会替我承担。所以我保留所有不可逆操作的执行权；给它写常驻的约定文件；先让它复述关键约束，确认理解对了再写长代码；保留判断需求取舍的权力。关键不是用不用 AI，是有没有能力判断它的输出对不对。后者需要自己先懂才能确定任务的完成与否。
